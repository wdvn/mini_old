# Advanced Rules and Guidelines for mini-agent

This document complements the sections above, focusing on **analysis, root cause investigation (RCA), and problem troubleshooting**.

## 1. Core Principles for Problem Analysis

1. **Investigate Before Mutating**:
   - Always locate the exact error origin and trace the data flow before modifying any code.
   - Use specialized analysis skills (`codebase-analysis`, `root-cause-analysis`, `session-diagnostics`) to gain complete situational awareness.

2. **Evidence-Based Diagnostics**:
   - When diagnosing runtime errors, inspect session logs under `~/.mini/sessions/journal_*.jsonl`.
   - Carefully review HTTP error codes, Zig's `error_name`, and backend server `raw_snippet` to prevent speculative assumptions.

3. **Align with RFCs & Design Docs**:
   - Before classifying a behavior as a "bug" or "feature", cross-reference the corresponding proposals in `docs/`.
   - Ensure proposed solutions conform to the project's Code-Centric (CodeAct VM) and Event Sourcing architectural direction.

4. **Multi-tier Verification**:
   - Reproduce issues with a concise unit test in `testcases/test_*.zig` when feasible.
   - After applying fixes, run the entire All-In-One test suite: `zig build test --summary all` (all 13/13 steps must pass).
     - *Tier 1 (Unit)*: Unit tests for core/tools/ui in `src/main.zig`.
     - *Tier 2 (Security/VM)*: CodeAct security, VM isolation, hooks, CAS file snapshots in `testcases/test_codeact_security.zig`.
     - *Tier 3 (E2E Mock LLM)*: Run `mini` binary against the mock OpenAI SSE server (`scripts/mock_llm_server.js`, 3 flows: simple text, long stream, multi-turn bash).
   - If isolated execution is needed: `zig build test-unit` (Tiers 1+2), `zig build test-e2e` (Tier 3), or `zig build test -Dskip-e2e=true`.

## 2. Standard RCA Workflow

```
[1. Intake & Problem Definition]
       │
       ▼
[2. Discovery & Evidence Gathering]
   ├── Read session logs: ~/.mini/sessions/journal_*.jsonl
   ├── Grep search affected areas in src/
   └── Review RFCs / Specs in docs/
       │
       ▼
[3. Hypothesis Formulation & Flow Tracing]
   ├── Map call-stack from Entry Point -> Core -> Runtime -> Backends
   └── Pinpoint breaking point / race condition / memory leak
       │
       ▼
[4. Hypothesis Verification]
   ├── Create reproduction testcase or detailed source trace
   └── Validate against Zig 0.16.0 constraints (memory, threading, I/O)
       │
       ▼
[5. Solution Proposal & Implementation]
   └── Make minimal edits, preserving existing conventions and comments
```

## 4. ReAct Mode & Structured Planning Guidelines

1. **Dual Execution Modes**:
   - **ReAct Mode (Reactive Execution — Default)**: For simple queries, exploratory searches, single-step commands, or quick inspections. Directly follow the ReAct loop:
     - `Thought`: Concise reasoning about the situation, analysis of previous observation, and immediate intent.
     - `Action`: Executable JavaScript (`mini.*`) inside a single ```js block.
     - `Observation`: Real data returned by QuickJS (`[CodeAct Execution Output]`). Never fabricate observations.
     - `Final Answer`: When done, output the final answer directly without code blocks.
     - *Zero planning overhead*: Do not emit multi-step plans for simple, single-action tasks.
   - **Proactive Planning Mode**: For complex or multi-step tasks (>= 2 steps, architectural refactors, multi-file edits). Formulate a structured JSON DAG plan or numbered checklist on turn 1, then execute each step sequentially via the ReAct cycle with progress tracking.
2. **Grounding in Active Code**:
   - Always verify facts against the active codebase using `mini.read`, `mini.grep`, or `mini.glob`.
   - Never guess file contents, function signatures, types, or configuration keys.
3. **Adaptive Cognitive Modulation (`mini.setThinking`)**:
   - Use `mini.setThinking("low")` for routine exploration and status inspections.
   - Use `mini.setThinking("high")` when analyzing root causes, debugging, or planning architecture.
4. **Surgical Implementation & Empirical Verification**:
   - Make minimal, precise changes (`mini.patch`).
   - Run relevant unit tests and build commands via `mini.sh(...)` after changes to empirically verify correctness.

# RULES

Behavioral guidelines to reduce common LLM coding mistakes. Merge with project-specific instructions as needed.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

---

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.

## 2. Simplicity First

### Example 1: Over-abstraction

**User Request:** "Add a function to calculate discount"

**❌ What LLMs Do (Overengineered)**

```python
from abc import ABC, abstractmethod
from enum import Enum
from typing import Protocol, Union
from dataclasses import dataclass

class DiscountStrategy(ABC):
    @abstractmethod
    def calculate(self, amount: float) -> float:
        pass

class PercentageDiscount(DiscountStrategy):
    def __init__(self, percentage: float):
        self.percentage = percentage
    
    def calculate(self, amount: float) -> float:
        return amount * (self.percentage / 100)

class FixedDiscount(DiscountStrategy):
    def __init__(self, fixed_amount: float):
        self.fixed_amount = fixed_amount
    
    def calculate(self, amount: float) -> float:
        return min(self.fixed_amount, amount)

@dataclass
class DiscountConfig:
    strategy: DiscountStrategy
    min_purchase: float = 0.0
    max_discount: float = float('inf')

class DiscountCalculator:
    def __init__(self, config: DiscountConfig):
        self.config = config
    
    def apply_discount(self, amount: float) -> float:
        if amount < self.config.min_purchase:
            return 0
        discount = self.config.strategy.calculate(amount)
        return min(discount, self.config.max_discount)

# Usage requires 30+ lines of setup for a simple calculation
```

**✅ What Should Happen (Simple)**

```python
def calculate_discount(amount: float, percent: float) -> float:
    """Calculate discount amount. percent should be 0-100."""
    return amount * (percent / 100)

# Usage
discount = calculate_discount(100.0, 10.0)  # $10 off
```

**When to add complexity:** Only when you actually need multiple discount types. If that requirement comes later, refactor then.

## Anti-Patterns Summary

| Principle | Anti-Pattern | Fix |
|-----------|-------------|-----|
| Think Before Coding | Silently assumes file format, fields, scope | List assumptions explicitly, ask for clarification |
| Simplicity First | Strategy pattern for single discount calculation | One function until complexity is actually needed |
| Surgical Changes | Reformats quotes, adds type hints while fixing bug | Only change lines that fix the reported issue |
| Goal-Driven | "I'll review and improve the code" | "Write test for bug X → make it pass → verify no regressions" |

## Key Insight

The "overcomplicated" examples aren't obviously wrong—they follow design patterns and best practices. The problem is **timing**: they add complexity before it's needed, which:

- Makes code harder to understand
- Introduces more bugs
- Takes longer to implement
- Harder to test

The "simple" versions are:
- Easier to understand
- Faster to implement
- Easier to test
- Can be refactored later when complexity is actually needed

## Security & Credentials

- **Credential Masking**: When sending data to LLM (prompts, tool outputs, file contents), mark sensitive credentials using `$Name` syntax instead of pasting raw values:
  - API keys → `$OPENAI_API_KEY`, `$ANTHROPIC_API_KEY`, etc.
  - Tokens → `$GITHUB_TOKEN`, `$AWS_ACCESS_KEY`, etc.
  - Secrets → `$DB_PASSWORD`, `$JWT_SECRET`, etc.
- This prevents leaking real secrets into LLM context, session logs, and history files.
- Resolve `$Name` placeholders locally in your environment before using them in shell commands or code.

- **Sensitive File Handling**: When reading or sharing content from the following file types, redact or mask sensitive values:
  - `.env`, `.env.local`, `.env.*.local` files → replace secret values with `$ENV_VAR_NAME`
  - YAML config files containing secrets (e.g., `config.yaml`, `secrets.yaml`, `values.yaml`) → mask key values that look like passwords, tokens, or API keys
  - JSON config files with credentials → use `$NAME` placeholders
- Rule of thumb: if a value looks like a secret (long random string, contains "password"/"secret"/"key"/"token", or is an API key format), mark it as `$VariableName`.
- Never commit `.env` files or files containing real credentials.
